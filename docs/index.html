An executable ability standard for agents

Give agents abilities they weren't born with.

Capability gives software agents a common way to discover an ability, understand it before running it, verify where it came from, ask for the right authority, execute it in isolation, safely replace or evolve it, and keep a receipt.

Why another layer?

Models can reason. APIs can expose services. MCP can connect tools. Package managers can distribute code. Capability focuses on the missing lifecycle: how does an agent gain an ability it wasn't prewired with, control what that ability may do, and know when a replacement is genuinely safe?

Discover before install

Agents can search inert descriptions and contracts without executing package code just to learn what it does.

Authority is visible

An ability declares what it may touch—filesystem, network, secrets, databases, email, Git, and more—before execution.

Evolution is inspectable

Capability can distinguish a safer replacement from one that silently expands authority or weakens its promises.

The whole path is one protocol.

Discovery is not trust. Installation is not authorization. Authorization is not isolation. A compatible-looking update is not automatically a safe substitution. Capability keeps those boundaries separate and makes them work together.

Research-informed agent-native primitives

Not another pile of wrapper functions.

The seed ecosystem includes abilities aimed at problems created by autonomous and dynamically extensible software itself.

capability/substitution-certificateSafe Substitution Certificate

Certifies a replacement only when its conservative contract still works, authority does not expand, behavioral guarantees do not weaken, and supplied trust posture does not regress.

capability/contract-evolutionContract Evolution Gate

Classifies upgrades using effects and behavioral promises as compatibility dimensions, not just function signatures and package version numbers.

capability/dominance-resolverDominance Resolver

Keeps the Pareto frontier of interchangeable abilities so a real safety-versus-trust tradeoff stays visible instead of disappearing into one magic score.

capability/novelty-radarNovelty Radar

Compares proposed abilities against the reachable ecosystem and flags likely functional twins before they become duplicate clutter.

capability/failure-frontierFailure Frontier

Finds a plan's first irreversible mutation, approval checkpoints, retry-safe prefix and compensation coverage before execution begins.

capability/receipt-driftReceipt Drift

Detects when apparently stable execution changes behavior, authority, verification result, package identity or package integrity.

capability/authority-envelopeAuthority Envelope

Shows the authority footprint of a planned set of abilities and exposes permission excess before an agent acts.

capability/contract-routerContract Router

Determines which downstream abilities can safely consume an upstream result by contract rather than model guesswork.

From zero to an ability

A new developer shouldn't need to learn Capability internals first.

npx @wheresmycoleslaw/capability create my-capability --id my-domain/my-ability cd my-capability npm install npm test npm run readiness npm run novelty

The generated project includes strict TypeScript, inert metadata, drift tests, packaging checks, CI, a tokenless trusted-publishing workflow, registry-entry generation, and novelty analysis against the live network.

Open the adoption guide

The standard wins only if strangers can extend it.

The technical adoption test is independent packages and independently hosted indexes interoperating without a special case added to Capability.

Build independently

Package authors own their implementation and release process.

Index independently

Anyone can host a valid capability index and federate it into other indexes.

Verify independently

The client verifies the chosen npm artifact instead of treating an index as a trust authority.
